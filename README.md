# Founder and Builder Posts

Twenty daily opportunities for short standalone X posts, generated by Cloudflare Workers AI. The old quote/repost workflow and trend discovery have been removed.

## Content

A daily mix of four founder connection posts, four product invitations, four coding opinions, four builder questions and four observations. Each opportunity has a distinct brief so the account does not repeat the same generic “let’s connect” request twenty times.

The voice is casual, playful and concise. Greetings can have one blank line before the invitation. Product invitations make any promise to try something conditional on a real need. Coding hot takes are framed as opinions or jokes. Posts stay below a conservative 260-character weighted ceiling; no Premium features are needed.

Cloudflare generates one candidate per request, with at most one correction attempt when output is malformed or repetitive. Each request has a fresh model seed and varied writing approach. A due post that exhausts both attempts fails visibly in Actions; a run with no post due remains a normal successful skip. Code rejects repeated wording, recycled sentence fragments, repeated openings, links, unsolicited mentions, trading engagement, unconditional product promises and unsupported numeric claims. Deterministic checks compare recent text and openings; related founder questions are allowed when their concrete wording differs. There is no second AI novelty veto, which previously rejected valid unrelated questions. These checks reduce repetition; they cannot guarantee perfect editorial judgment.

## Variable daily timing

The UTC day has 20 bands of 72 minutes. A date-seeded random minute (10–40 minutes into each band) and a shuffled content mix create a new timetable each day. The timetable is reproducible within the day, so retries cannot keep moving a slot. Planned slots are at least 42 minutes apart, with a 30-minute publication guard.

The **Publish Founder and Builder Posts** workflow checks every 15 minutes; the existing external `post-next` dispatcher is also supported. GitHub scheduling and runner delays affect actual delivery. This is a changing daily timetable rather than a fixed daily posting time; it is not second-accurate scheduling.

Only the latest due opportunity can run. Missed earlier opportunities expire, so downtime cannot produce a catch-up burst. Twenty is the daily target and hard maximum, not a guarantee during outages or when every candidate fails validation. The launch begins with the latest due opportunity, so a partial launch day has fewer posts. Later full days have 20 opportunities.

## Setup and secrets

Existing GitHub Actions secrets are reused:

- `X_AUTH_TOKEN` and `X_CT0` for the existing X session client.
- `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` for Workers AI.
- Optional repository variable `CLOUDFLARE_AI_MODEL`; default `@cf/meta/llama-3.1-8b-instruct-fp8`.

No secret values are read from GitHub or printed. No paid plan or billing upgrade is enabled. Existing Cloudflare allocation, token permissions and X session validity still apply. The session client is retained at the owner's request and can break or be restricted by X.

Code pushes start a run. Use workflow dispatch to run it manually or disable the workflow in Actions to stop it. `python -m app preview` generates a preview without changing state. `python -m app prepare --start-now` starts the first opportunity immediately if none has been published; after launch it obeys the normal timetable and cap.

## Publication and crash protection

Active state is `state/community_queue.json`. The old `state/post_queue.json` is a retired record and is never read by the standalone publisher.

The workflow generates and saves a reservation, commits and pushes it, then attempts `create_tweet(text=...)` once. It never attaches a quoted post or posts an automated reply. Confirmation with a real X ID is then committed. If a timeout, missing ID, canceled run or failed final push leaves a reservation unresolved, later runs stop rather than risk duplicate publication.

To recover, disable the workflow and inspect X. If the reserved text was published, record the real `tweet_id`, `slot`, `category`, `text`, and `posted_at` in history, update `last_posted_at`, and clear `pending`. If definitely not published, clear `pending`. Commit the correction before re-enabling. Never clear a reservation merely because a job failed.

The changes affect future automation; posts already on X are not deleted.

## Verification

```sh
python -m pip install -r requirements.txt
python -m compileall -q app
python -m unittest discover -s tests -v
```

Tests cover the changing timetable, daily cap, interval, expired opportunities, duplicate text, candidate selection, Cloudflare request format, standalone publishing and uncertain-outcome recovery. Check the real post link in the workflow summary to confirm live delivery.
